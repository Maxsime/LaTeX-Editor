# J9 — Assistant IA : plan

Statut : plan rédigé le 2026-10-27 et appliqué sans attendre de validation, à la demande de Maxime (enchaîner les jalons jusqu'au J11, les plans étant relus plus tard). Les points à trancher sont réglés par la recommandation indiquée.

Références : `SPEC.md` §3.8 (assistant IA), §3.9 (préférence de fournisseur), §6.1 (tables `ai_*`), §6.2 (source de vérité Yjs), §6.3 (bac à sable), §6.8 (couche IA), §9 J9 ; `CLAUDE.md` (clés chiffrées au repos, jamais renvoyées au-delà des quatre derniers caractères, aucun secret ni contenu de document dans les journaux, aucune modification de fichier sans validation explicite).

## Objectif

Un assistant qui connaît le projet, répond en flux, propose des modifications sous forme de différentiel que l'utilisateur accepte ou rejette, génère tableaux, figures et formules avec un aperçu compilé, convertit une image en LaTeX et ajoute au `.bib` des entrées issues d'API bibliographiques, jamais rédigées par le modèle.

## Critères d'acceptation (SPEC §9)

- A1. Un même scénario fonctionne avec Anthropic et avec un modèle local via Ollama.
- A2. Aucun fichier n'est modifié avant acceptation.
- A3. Une clé de citation inventée est rejetée par le serveur.
- A4. La clé API n'apparaît dans aucune réponse HTTP ni dans aucun log.

## Existant

- `projects.ai_enabled` existe dans le schéma (défaut vrai), sans route ni interface.
- `SecretBox` (AES-256-GCM, clé maître `GALLEY_MASTER_KEY`, contexte lié au chiffré) et `keyHint` servent déjà à la clé Zotero.
- Recherche par DOI (Crossref), arXiv et ISBN (Open Library), génération BibTeX et clés normalisées : `apps/api/src/bibliography/`.
- `readProjectTexts` lit le contenu courant de tous les fichiers texte après écriture des documents tenus par collab ; `searchFiles` cherche dans le projet ; l'index (`latex-index`) donne plan, labels, clés, paquets et commandes.
- collab expose des routes internes (`flush`, `replace`, `close`) protégées par jeton ; une connexion directe Hocuspocus porte un contexte que `onChange` lit pour attribuer les auteurs de l'instantané suivant.
- La file de compilation accepte un manifeste quelconque ; le verrou et le répertoire de travail sont indexés par `projectId`.

## Conception

### Paquet `packages/ai`

- Dépendances : `ai` (Vercel AI SDK 7), `@ai-sdk/anthropic`, `@ai-sdk/openai`, `@ai-sdk/mistral`, `@ai-sdk/openai-compatible`, versions exactes publiées depuis plus de deux semaines. Paquet serveur uniquement : rien n'arrive dans le bundle du navigateur.
- `createModel(config)` : fournisseur (`anthropic`, `openai`, `mistral`, `openai-compatible`), modèle, clé, URL de base.
- `capabilitiesOf(provider, model)` : vision, outils, taille de contexte, cache de prompt. Table de motifs pour les familles connues (Claude, GPT-4o/4.1/5, o-series, Mistral Large/Medium, Pixtral), valeurs prudentes sinon (outils oui, vision non, 32 k jetons, pas de cache), surchargeables pour l'instance (`AI_DEFAULT_VISION`, `AI_DEFAULT_CONTEXT_TOKENS`).
- `buildContext` (pur) : préfixe stable (arborescence, plan, labels, clés de citation, paquets, commandes définies), puis partie variable (fichier courant tronqué autour du curseur, sélection, erreurs du dernier journal). Budget en caractères dérivé de la taille de contexte du modèle. Le préfixe porte un point de cache Anthropic (`cacheControl: ephemeral`).
- Prompts versionnés dans `packages/ai/prompts/` (`chat.v1.md`, `inline.v1.md`, `fix.v1.md`, `generate.v1.md`, `image.v1.md`), lus au démarrage ; leur version figure dans le journal d'usage.
- Définition des outils (schémas Zod) : `list_files`, `read_file(path, startLine?, endLine?)`, `search_project(pattern, regex?)`, `get_outline`, `get_compile_log`, `compile_snippet(latex)`, `propose_changes(edits[])`, `search_literature(query)`, `fetch_bibtex(doi | arxivId | isbn)`. L'exécution est injectée par l'API (`ToolHost`) : le paquet ne touche ni base ni réseau du projet.
- `runAssistant` : boucle d'outils bornée (8 étapes, plafond de jetons de sortie), flux d'événements typés (`text`, `tool`, `changeset`, `snippet`, `usage`, `error`).
- `estimateCost(usage, price)` (pur) à partir de `ai_model_prices`.
- Suite d'évaluation `packages/ai/eval/` : scénarios fixes (corriger une coquille, générer un tableau, une formule, une figure TikZ). `pnpm --filter @galley/ai eval` les joue contre le modèle configuré par variables d'environnement et vérifie que le résultat compile (pdflatex local ou image `galley/compiler`). En CI, le même harnais tourne contre un modèle simulé pour garantir que prompts et analyse des réponses restent cohérents.

### Configuration des fournisseurs

- Configuration d'instance par variables d'environnement : `AI_ENABLED` (interrupteur global, défaut vrai), `AI_DEFAULT_PROVIDER`, `AI_DEFAULT_MODEL`, `AI_DEFAULT_BASE_URL`, `AI_DEFAULT_API_KEY`. La console d'administration du J10 pourra les surcharger en base.
- Configuration personnelle (`ai_provider_configs`, une ligne par utilisateur) : fournisseur, modèle, clé chiffrée (contexte `ai:<userId>`), indice de quatre caractères. Routes `GET|PUT|DELETE /api/me/ai/provider`. La clé est en écriture seule : aucune route ne la renvoie.
- URL de base personnalisée : réservée à l'administrateur par défaut. Un utilisateur ne peut choisir qu'Anthropic, OpenAI ou Mistral à leurs adresses officielles, sauf si `AI_ALLOW_USER_ENDPOINTS=true`. Raison : une URL libre ferait appeler par l'API des services internes (PostgreSQL, collab) au nom de l'utilisateur (SSRF).
- Ollama sur la machine hôte : `AI_DEFAULT_PROVIDER=openai-compatible`, `AI_DEFAULT_BASE_URL=http://host.docker.internal:11434/v1`. `compose.yaml` ajoute `host.docker.internal` à l'API (`host-gateway`), déjà présent sous Docker Desktop, à ajouter sous Linux.
- Résolution : configuration personnelle si présente, sinon celle de l'instance, sinon assistant indisponible. Un projet avec `ai_enabled = false` ou une instance avec `AI_ENABLED=false` refuse toute requête IA (`AI_DISABLED`) et l'interface masque le panneau.

### Discussion en flux

- `POST /api/projects/:id/ai/chat` (éditeur et plus pour proposer des modifications, lecteur pour discuter) : `{ conversationId?, mode: 'chat' | 'inline' | 'fix' | 'generate' | 'image', messages, context: { fileId?, cursor?, selection? }, diagnostic?, image? }`, validé par Zod (taille des messages bornée, image PNG, JPEG ou WebP de 4 Mo au plus, refusée si le modèle n'a pas la vision).
- Réponse `text/event-stream` (un événement JSON par ligne `data:`), schémas dans `packages/shared`. Pas de dépendance client : le navigateur lit le flux avec `fetch`.
- Conversation : identifiant créé par le serveur au premier message, état dans Valkey (TTL 24 h) : propriétaire, projet, entrées BibTeX obtenues par `fetch_bibtex`. L'historique des messages reste côté client et repart à chaque requête (texte seulement : un client ne peut pas forger un résultat d'outil qui compterait pour le contrôle des citations).
- Modes :
  - `chat` : outils complets ;
  - `inline` : sélection et consigne, sans outil ; la réponse (bloc de code) devient un hunk unique sur la sélection ;
  - `fix` : diagnostic du journal (fichier, ligne, message), explication puis `propose_changes` ;
  - `generate` et `image` : le modèle rend un bloc `latex` (corps) et un bloc `latex-preamble` facultatif ; il peut vérifier par `compile_snippet` ; le serveur compile toujours le résultat final pour l'aperçu.
- Limites : 20 requêtes par minute et par personne (`AI_RATE_LIMIT_PER_MINUTE`), délai global de 120 s, 8 étapes d'outils.
- Erreurs du fournisseur traduites en codes stables (`AI_AUTH_FAILED`, `AI_RATE_LIMITED`, `AI_UNAVAILABLE`, `AI_BAD_RESPONSE`). Les objets d'erreur du SDK contiennent le corps de la requête (donc le document) : seuls leur nom et leur statut HTTP sont journalisés.

### Changesets

- `propose_changes(edits[])`, une modification étant `{ path, search, replace }` : `search` doit apparaître exactement une fois dans le fichier (sinon erreur renvoyée au modèle, qui corrige) ; `search` vide sur un chemin inexistant crée un fichier texte. Le serveur calcule les hunks (position, texte d'origine, remplacement, 40 caractères de contexte avant et après).
- Stockage dans Valkey (TTL 24 h), pas en base : un changeset est une proposition éphémère, pas une seconde copie des fichiers (`SPEC.md` §6.2).
- Contrôle des citations côté serveur, à la proposition puis à l'application :
  - toute clé de `\cite` et variantes (`latex-index`) d'un remplacement doit exister dans un `.bib` du projet ou provenir d'un `fetch_bibtex` de la conversation ; une clé déjà présente dans le texte d'origine reste admise ;
  - toute entrée ajoutée à un `.bib` doit être identique (espaces normalisés) à une entrée obtenue par `fetch_bibtex` dans la conversation ;
  - violation à la proposition : changeset refusé, erreur `UNKNOWN_CITATION` rendue au modèle ; violation à l'application (entrée supprimée entre-temps) : hunk refusé.
- `POST /api/projects/:id/ai/changesets/:changesetId/apply` `{ hunkIds }` (éditeur et plus, auteur du changeset) et `.../reject`. Accepter tout, un fichier ou un hunk revient à choisir les identifiants.
- Application dans collab par une nouvelle route interne `POST /internal/documents/:fileId/edit` `{ userId, hunks }` : une seule transaction Yjs sur une connexion directe dont le contexte est `{ userId, origin: 'ai:<userId>' }`. L'utilisateur devient auteur de l'instantané suivant ; l'origine figure dans la transaction. Recalage (module pur `realignHunks` de `packages/shared`) :
  1. le texte d'origine est toujours à sa position : appliqué ;
  2. sinon, occurrence unique du texte d'origine, ou occurrence dont le contexte correspond, la plus proche de la position initiale : appliqué à la nouvelle position ;
  3. sinon, ou si deux hunks se chevauchent : conflit, rien n'est écrit pour ce hunk.
- Un projet en mode suivi des modifications (J7) reçoit quand même une écriture directe : l'acceptation vaut validation de l'auteur.

### Compilation d'extraits

- `compile_snippet` et l'aperçu final passent par la file de compilation existante : un manifeste d'un seul fichier `main.tex` (document `standalone` avec `varwidth`), pdfLaTeX, arrêt à la première erreur. Le `projectId` du job est un UUID dérivé de `(projet, utilisateur)` : verrou et répertoire de travail propres, sans collision avec la compilation du projet. Nom de job `snippet`, ignoré par le suivi des compilations du projet.
- L'API attend la fin du job (30 s au plus) et rend diagnostics et identifiant d'aperçu. `GET /api/projects/:id/ai/snippets/:compileId.pdf` sert le PDF à son seul demandeur (propriété notée dans Valkey, TTL 1 h).

### Recherche bibliographique

- `search_literature(query)` : Crossref (`/works?query=`), arXiv (`search_query=all:`), OpenAlex (`/works?search=`) en parallèle ; Semantic Scholar seulement si `SEMANTIC_SCHOLAR_API_KEY` est défini (le service limite fortement les appels anonymes). Résultats fusionnés par DOI, 10 au plus : titre, auteurs, année, DOI, identifiant arXiv.
- `fetch_bibtex` réutilise les recherches du J8 et le motif de clés du projet ; l'entrée est notée dans la conversation.

### Consommation

- `ai_usage` : utilisateur, projet, fournisseur, modèle, mode, version du prompt, jetons d'entrée, de sortie et lus en cache, coût estimé en micro-euros (nul si le prix est inconnu), date.
- `ai_model_prices` : fournisseur, modèle, prix par million de jetons (entrée, sortie, cache), devise. Routes d'administration `GET|PUT /api/admin/ai/prices` ; l'écran correspondant arrive avec la console du J10. Aucun prix n'est préchargé : ils changent souvent et un prix faux serait pire qu'un coût affiché comme inconnu.
- Événement `usage` en fin de réponse (affiché sous le message) ; `GET /api/me/ai/usage` pour le cumul du mois et par modèle (page Compte).

### Interface

- Panneau « Assistant » dans la barre latérale du projet : messages en flux, activité des outils, cartes de changeset avec différentiel par hunk (ligne supprimée et ligne ajoutée), boutons Accepter et Rejeter par hunk, par fichier et pour tout, conflits signalés, consommation sous chaque réponse.
- Édition en ligne : `Ctrl+Alt+K` sur une sélection ouvre un champ de consigne ; la proposition s'affiche dans l'éditeur (texte d'origine barré, remplacement en widget, boutons Accepter et Rejeter) et dans le panneau.
- Journal : bouton « Expliquer et corriger » sur chaque erreur.
- Barre d'insertion : « Générer… » (tableau, figure TikZ ou pgfplots, formule, à partir d'une description ou d'une image si le modèle a la vision), aperçu compilé puis « Insérer » au curseur et paquets manquants signalés.
- Options du projet (propriétaire) : case « Assistant IA ». Page Compte : fournisseur, modèle, clé (indice seul), consommation.
- Textes via i18n (français, anglais).

## Modèle de données

- `ai_provider_configs` : `user_id` (PK, FK), `provider`, `model`, `base_url` (nul), `key_ciphertext` (nul), `key_hint` (nul), dates.
- `ai_usage` : `id`, `user_id`, `project_id` (nul si supprimé), `provider`, `model`, `mode`, `prompt_version`, `input_tokens`, `output_tokens`, `cached_input_tokens`, `cost_micros` (nul), `created_at` ; index `(user_id, created_at)`.
- `ai_model_prices` : `(provider, model)` PK, `input_per_mtok`, `output_per_mtok`, `cached_input_per_mtok`, `currency`, `updated_at`.

## Découpage en tâches

1. `packages/ai` : fournisseurs, capacités, contexte, prompts, définition des outils, boucle, coût ; tests unitaires.
2. `packages/shared` : schémas (requêtes, événements du flux, changesets, configuration), `realignHunks` avec tests de propriétés.
3. Migration Drizzle des trois tables ; configuration d'environnement.
4. collab : route interne `edit` ; tests.
5. API : configuration fournisseur, statut, discussion en flux, exécution des outils, changesets et citations, extraits compilés, recherche bibliographique, consommation, prix ; tests d'intégration avec faux serveurs Anthropic et compatible OpenAI.
6. compiler : rien à changer (le job d'extrait est un job ordinaire) ; API : job `snippet` ignoré par le suivi.
7. Web : panneau, différentiel, édition en ligne, corriger, générer, image, réglages, consommation, option de projet ; i18n.
8. e2e : scénario complet contre un faux fournisseur compatible OpenAI lancé par le test (joint par `host.docker.internal`).
9. Documentation : README, `docs/operations.md` (fournisseurs, Ollama, confidentialité), `docs/decisions.md`, `.env.example`.

## Tests des critères

- A1 : le même scénario (lecture d'un fichier par outil, proposition, acceptation, vérification du contenu) tourne dans les tests d'intégration contre un faux serveur au protocole Anthropic (Messages API en flux) et un faux serveur au protocole OpenAI (celui d'Ollama), avec les vrais adaptateurs du SDK. Un essai réel avec Anthropic et Ollama est décrit dans `docs/operations.md` pour validation manuelle.
- A2 : même test, contenu inchangé après la proposition puis modifié après acceptation ; e2e identique dans le navigateur.
- A3 : proposition avec `\cite{inventee2099}` refusée (outil en erreur, aucun changeset) ; application refusée si l'entrée a disparu entre-temps.
- A4 : clé fictive reconnaissable enregistrée, toutes les réponses HTTP du test et toute la sortie pino capturée sont parcourues : seule la forme à quatre caractères apparaît. Y compris quand le fournisseur répond 401.

## Points tranchés

- Changesets et conversations dans Valkey avec TTL plutôt qu'en base (§6.2, rien à purger).
- Historique de discussion côté client, non persisté : suffisant en P1, sans stockage de contenu.
- URL de base libre réservée à l'instance (SSRF), sauf option explicite.
- Prix des modèles non préchargés.
- Configuration d'instance par variables d'environnement jusqu'à la console du J10.
- Différentiel affiché sans bibliothèque (hunks courts, lignes supprimées puis ajoutées).

## Risques

- Modèles locaux faibles en appel d'outils : le mode `inline` et la génération n'en dépendent pas ; le chat dégrade en réponse texte.
- Écart d'API entre versions du SDK : versions exactes et tests contre les vrais adaptateurs.
- Coût et abus : limite de débit, plafond de jetons, désactivation par projet et par instance.
