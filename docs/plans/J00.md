# J0 — Fondations : plan

Statut : plan validé le 2026-10-26, jalon réalisé (bilan en fin de document).
Références : `SPEC.md` §4 (pile), §5 (architecture), §7 (exigences non fonctionnelles), §9 J0 ; `CLAUDE.md` (méthode, définition de « terminé », conventions, sécurité).

## Objectif

Disposer d'un monorepo outillé et d'une instance Docker Compose complète dont chaque service démarre, se déclare sain et est testé en CI. Aucune fonctionnalité métier : uniquement le socle sur lequel J1 à J10 s'appuieront.

Critères d'acceptation (SPEC §9) :

- A1. `docker compose up` amène tous les services à l'état sain.
- A2. CI verte.
- A3. Page d'accueil servie en HTTPS local.

## Périmètre

Inclus : monorepo, lint, format, typecheck, tests, `packages/shared`, chargement de configuration validé par Zod, migrations Drizzle, squelettes `api`, `collab`, `compiler`, `web`, Docker Compose (PostgreSQL 16, Valkey, SeaweedFS en remplacement de MinIO, Caddy), CI, documentation.

Exclus et reportés :

- TeX Live et bubblewrap dans l'image `compiler` : J3. Le squelette J0 repose sur une image Node seule (voir P4).
- LanguageTool : J8, seul jalon qui l'utilise.
- `packages/latex-log`, `latex-index`, `ai`, `ui` : créés au jalon qui les utilise, pour ne pas versionner de paquets vides.
- Toute table métier : J1.

## Découpage en tâches

Chaque tâche donne lieu à un ou plusieurs commits atomiques.

### T1. Socle du monorepo

- pnpm workspaces, Turborepo (`build`, `lint`, `typecheck`, `test`, `dev` avec dépendances et cache).
- `packageManager` figé dans `package.json`, `.nvmrc` (Node 22 LTS), `engines`.
- `tsconfig.base.json` : `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, références de projet.
- ESLint 9 en configuration plate, `typescript-eslint` en mode `strict-type-checked`, règles interdisant `any` et les assertions `as` non commentées, `eslint-plugin-react-hooks` pour `web`.
- Prettier, `.editorconfig`, `.gitignore` (dont `.env`), `.gitattributes`.
- Scripts racine : `lint`, `typecheck`, `format`, `test`, `test:e2e`, `dev`.

Fichiers : `package.json`, `pnpm-workspace.yaml`, `turbo.json`, `tsconfig.base.json`, `eslint.config.js`, `.prettierrc`, `.editorconfig`, `.nvmrc`, `.gitignore`, `.gitattributes`.

### T2. `packages/shared` et configuration

- Schémas Zod des variables d'environnement, un par service, construits à partir de fragments communs (PostgreSQL, Valkey, stockage S3, journalisation).
- `loadConfig(schema, env)` : validation au démarrage, arrêt immédiat avec la liste des variables fautives, sans jamais afficher de valeur secrète.
- Schéma de la réponse des points de santé, partagé par tous les services.
- Fabrique de logger pino commune : niveau, champ `service`, liste de rédaction (`authorization`, `cookie`, clés et jetons).

Fichiers : `packages/shared/src/{env,health,logger,index}.ts` et tests associés.

### T3. Service `api`

- Fastify, `fastify-type-provider-zod`, identifiant de requête propagé dans les logs.
- `GET /api/health/live` (processus vivant) et `GET /api/health/ready` (PostgreSQL, Valkey et stockage S3 joignables, détail par dépendance).
- `GET /metrics` au format Prometheus (`prom-client`), non exposé par Caddy.
- Format d'erreur typé (code machine stable, clé i18n), gestionnaire d'erreurs qui ne renvoie jamais de trace.
- Drizzle ORM : `drizzle.config.ts`, dossier `migrations/` versionné, application des migrations au démarrage sous verrou consultatif PostgreSQL (plusieurs instances ne migrent pas en parallèle). Migration initiale limitée à l'extension `citext` utile dès J1 (`gen_random_uuid` est natif depuis PostgreSQL 13, `pgcrypto` est donc inutile).
- Création idempotente du bucket S3 au démarrage, pour respecter « aucune intervention manuelle ».
- Arrêt propre sur `SIGTERM` (fermeture des connexions, fin des requêtes en cours).

Fichiers : `apps/api/src/{server,app,config,db/*,storage/*,routes/health,errors}.ts`, `apps/api/migrations/`, `apps/api/Dockerfile`.

### T4. Service `collab`

- Hocuspocus avec l'extension Redis branchée sur Valkey ; extension Database déclarée mais sans persistance réelle (arrive au J2).
- Point de santé HTTP sur le même port (Valkey joignable), métriques Prometheus minimales (connexions ouvertes).
- Authentification refusant par défaut toute connexion WebSocket tant que J5 n'a pas implémenté le contrôle d'accès : on part fermé, pas ouvert.

Fichiers : `apps/collab/src/{server,config,health}.ts`, `apps/collab/Dockerfile`.

### T5. Service `compiler`

- Worker BullMQ abonné à la file `compile`, avec un gestionnaire qui rejette toute tâche (« non implémenté ») et un schéma Zod de tâche conforme à SPEC §6.3, posé dans `packages/shared`.
- Petit serveur HTTP de santé (Valkey joignable) et métriques.
- Image Node seule à ce stade.

Fichiers : `apps/compiler/src/{worker,config,health}.ts`, `packages/shared/src/compile-job.ts`, `apps/compiler/Dockerfile`.

### T6. Application `web`

- Vite, React 19, TanStack Router (routes typées), TanStack Query, Zustand, Tailwind CSS, Radix UI installé mais non utilisé au-delà d'un composant.
- i18n dès J0 : français par défaut, anglais, détection navigateur, aucun texte en dur.
- Page d'accueil : nom du produit, version, état de l'API interrogé sur `/api/health/ready`, sélecteur de langue.
- CSP stricte posée dans Caddy dès maintenant (`default-src 'self'`), pour ne pas avoir à la resserrer plus tard.

Fichiers : `apps/web/{index.html,vite.config.ts,src/**}`, `apps/web/src/locales/{fr,en}.json`.

### T7. Caddy et Docker Compose

- Image Caddy construite en plusieurs étapes : compilation de `web`, puis copie du `dist` dans l'image Caddy. Caddy sert la SPA, proxifie `/api/*` vers `api` et `/collab` (WebSocket) vers `collab`.
- HTTPS local par `tls internal` (autorité de certification interne de Caddy) sur `https://localhost` par défaut, nom d'hôte paramétrable par `GALLEY_HOST`. Racine de l'AC exportée dans un volume pour pouvoir l'installer dans le navigateur ; procédure dans le README.
- `compose.yaml` : `postgres:16`, `valkey/valkey:8`, `chrislusf/seaweedfs` (mode `server -s3`), `api`, `collab`, `compiler`, `caddy` ; versions d'images figées ; `healthcheck` sur chaque service ; `depends_on: condition: service_healthy` ; volumes nommés ; réseaux séparés (Caddy ne voit ni PostgreSQL ni le stockage S3).
- `compose.dev.yml` : dépendances seules, ports exposés en local pour `pnpm dev`.
- Dockerfiles Node multi-étapes avec `pnpm deploy` (image finale sans dépendances de développement), utilisateur non root, `tini` ou `--init` pour la propagation des signaux.
- `.env.example` complet, commenté ; valeurs par défaut suffisantes pour un démarrage local sans modification, secrets de production obligatoires hors du mode développement.

Fichiers : `compose.yaml`, `compose.dev.yml`, `infra/caddy/{Caddyfile,Dockerfile}`, `.env.example`, `.dockerignore`.

### T8. Tests

- Vitest en mode projets (un projet par paquet) ; seuil de couverture appliqué aux modules purs de `packages/shared`.
- Unitaires : `loadConfig` (valeurs valides, manquantes, malformées, secret jamais affiché), schémas de santé, format d'erreur.
- Intégration avec Testcontainers : `api` démarré contre PostgreSQL, Valkey et SeaweedFS réels ; vérification de `/ready`, de l'application des migrations, de l'idempotence (deux démarrages), de la création du bucket et du passage à « non prêt » quand une dépendance tombe.
- e2e Playwright contre la pile Compose : la page d'accueil se charge en HTTPS (certificat de l'AC interne fourni à Playwright, pas de `ignoreHTTPSErrors`), affiche l'état de l'API, bascule français/anglais ; la redirection HTTP vers HTTPS fonctionne.
- Script `scripts/compose-healthy.sh` : `docker compose up --build --wait` puis contrôle que chaque service est `healthy` (couvre A1).

Correspondance critères et tests : A1 par `compose-healthy.sh` en CI ; A2 par le workflow lui-même ; A3 par le test e2e HTTPS.

### T9. Intégration continue

GitHub Actions, déclenchée sur push et pull request :

1. `lint`, `typecheck`, `test` (Testcontainers sur le Docker de l'exécuteur), avec cache pnpm et Turborepo.
2. Construction des images avec Buildx et cache GitHub Actions.
3. `compose-healthy.sh` puis `pnpm test:e2e` sur la pile construite ; journaux des conteneurs archivés en cas d'échec.
4. `pnpm audit --audit-level=high` (SPEC §7).

Fichiers : `.github/workflows/ci.yml`.

### T10. Documentation

- `README.md` : présentation, prérequis, démarrage en une commande, installation de l'AC locale, commandes de développement.
- `docs/decisions.md` : premières entrées (voir plus bas).
- `docs/architecture.md` : services, ports, réseaux, points de santé.

## Décisions techniques prises (à consigner dans `docs/decisions.md`)

- i18n : `i18next` et `react-i18next`, bibliothèque la plus maintenue et compatible avec un chargement paresseux des langues.
- Métriques : `prom-client`.
- Migrations appliquées par `api` au démarrage, sous verrou consultatif.
- Bucket S3 créé par `api` plutôt que par un conteneur d'initialisation, pour limiter les pièces mobiles.
- Point de santé `live` distinct de `ready` dans chaque service.
- `collab` refuse toute connexion tant que le contrôle d'accès n'existe pas.

## Risques

- R1. MinIO : vérifié le 2026-10-26, les images Docker communautaires ne sont plus publiées et le dépôt source est archivé. Remplacé par SeaweedFS (voir P1).
- R2. Confiance dans le certificat local : navigateurs et Playwright rejettent l'AC interne de Caddy tant qu'elle n'est pas installée. Mitigation : export de la racine, procédure documentée, injection dans Playwright.
- R3. Testcontainers en CI et dans un environnement sans Docker : les tests d'intégration seront ignorés proprement en local sans Docker, mais obligatoires en CI (échec si Docker absent en CI, pour ne pas masquer un trou).
- R4. Compatibilité des versions majeures récentes (React 19 et TanStack Router, Tailwind 4, ESLint 9, Hocuspocus 3) : versions figées, vérification d'une construction complète dès T1 à T6.
- R5. Durée de la CI : la construction des images et la pile Compose rallongent chaque exécution. Mitigation : cache Buildx, e2e lancés après les étapes rapides.
- R6. Lint typé lent sur un gros monorepo : `projectService` de `typescript-eslint` et cache Turborepo.

## Points à trancher

- P1. Stockage S3 : tranché. MinIO est remplacé par SeaweedFS en mode S3 (licence Apache-2.0, maintenu, démarrage en un seul conteneur sans étape d'initialisation manuelle, contrairement à Garage qui exige d'appliquer une topologie). Le code n'utilise que l'API S3 via `@aws-sdk/client-s3`, ce qui garde le fournisseur interchangeable. Décision consignée dans `docs/decisions.md` comme modification de SPEC §4.
- P2. Dépôt et CI : tranché. Dépôt `github.com/Maxsime/LaTeX-Editor`, CI sous GitHub Actions.
- P3. Adresse locale : tranché. `https://localhost` par défaut, paramétrable par `GALLEY_HOST`. L'hébergement public (VPS et nom de domaine) relève du J10.
- P4. Image `compiler` : tranché. TeX Live est intégré au J3.
- P5. Licence : tranché. AGPL-3.0, fichier `LICENSE` ajouté au premier commit (T1). Rappel : cette licence n'autorise pas pour autant à reprendre du code d'Overleaf, l'interdit de `CLAUDE.md` reste en vigueur.

## Bilan (2026-10-26)

### Ce qui fonctionne

- A1 : `docker compose up --build` démarre les sept services (`postgres`, `valkey`, `storage`, `api`, `collab`, `compiler`, `caddy`) jusqu'à l'état sain, sans configuration préalable. Couvert par `scripts/compose-healthy.sh`, exécuté en CI.
- A2 : CI GitHub Actions en trois tâches : lint, types et tests (dont intégration Testcontainers) ; audit des dépendances ; construction des images, démarrage de la pile et tests e2e.
- A3 : page d'accueil servie en HTTPS par l'autorité locale de Caddy. Les tests e2e vérifient le certificat pour de bon (Node via `NODE_EXTRA_CA_CERTS`, Chromium par liste blanche des clés de l'autorité), sans ignorer les erreurs TLS.
- Configuration validée par Zod dans chaque service, erreurs listant les variables sans leurs valeurs.
- Migrations Drizzle appliquées au démarrage sous verrou consultatif, testées en concurrence.
- Erreurs d'API typées (code stable, clé i18n, identifiant de requête), jamais de trace renvoyée.
- Logs pino structurés avec identifiant de requête propagé depuis Caddy, liste de rédaction des secrets.
- Métriques Prometheus sur chaque service, non exposées publiquement.
- Interface en français et en anglais, détection de la langue du navigateur, lien vers les sources (AGPL-3.0 §13).
- CSP stricte, HSTS et en-têtes de sécurité posés par Caddy ; aucune violation CSP relevée par les tests e2e.

Tests : 39 unitaires dans `shared`, 14 dans `api` (dont 4 d'intégration), 6 dans `collab`, 5 dans `compiler`, 5 dans `web`, 8 e2e.

### Écarts par rapport au plan

- MinIO remplacé par SeaweedFS (P1), consigné dans `docs/decisions.md`.
- Schémas partagés en `zod/mini` : la forme classique ajoutait 90 kB gzip au bundle du navigateur.
- `fastify-type-provider-zod` non installé : aucune route n'a encore de corps à valider. À introduire au J1 avec les premières routes métier.
- Extension Database de Hocuspocus non déclarée : sans persistance, elle n'aurait rien apporté. Elle arrive au J2 avec `yjs_states`.
- Zustand non installé : aucun état client partagé au J0.
- tini fourni par l'init de Docker (`init: true`) plutôt qu'installé dans l'image.
- `pnpm deploy` remplacé par une installation `--prod` hors ligne depuis le lockfile, qui garantit des images reproductibles.

### Ce qui reste et dette identifiée

- Le bundle de l'interface pèse 140 kB gzip (React DOM, TanStack Router et Query, i18next, Radix). Aucune dépendance ne dépasse 100 kB ; le découpage en morceaux sera utile quand CodeMirror et PDF.js arriveront.
- La règle « pas d'assertion `as` sans commentaire » n'est pas vérifiable par ESLint ; elle repose sur la relecture.
- Les secrets par défaut de `compose.yaml` conviennent au local uniquement. Un refus de démarrer avec ces valeurs sur une instance publique est à prévoir au J10.
- Valkey n'a pas de mot de passe ; il n'est joignable que depuis le réseau interne `data`.
- `pnpm audit` signale une vulnérabilité modérée dans un ancien esbuild tiré par `drizzle-kit`, outil de développement absent des images ; elle reste sous le seuil bloquant (`high`).
- L'autorité locale de Caddy doit être installée à la main dans le navigateur ; la procédure est dans le README.
