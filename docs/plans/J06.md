# J6 — Historique et Git : plan

Statut : plan rédigé le 2026-10-27 et appliqué sans attendre de validation, à la demande de Maxime (enchaîner les jalons jusqu'au J11, les plans étant relus plus tard). Les points à trancher sont réglés par la recommandation indiquée.
Références : `SPEC.md` §3.5 (historique et Git), §4 (`git` natif, smart HTTP via `git http-backend`), §6.1 (`snapshots`, `personal_access_tokens`), §6.2 (`materializeProject`), §6.7 (historique et pont Git), §9 J6 ; `CLAUDE.md` (chemins, tailles de push, jetons).

## Objectif

Garder la trace de chaque état d'un projet, le comparer, le restaurer sans rien perdre, et rendre chaque projet clonable avec Git, dans les deux sens et en direct.

Critères d'acceptation (SPEC §9) :

- A1. `git clone`, modification locale et `git push` sont visibles en direct dans un éditeur ouvert.
- A2. Une modification faite dans l'éditeur est récupérée par `git pull`.
- A3. La restauration d'une version ancienne ne perd aucun historique.

## Existant

`materializeProject` produit déjà le manifeste `{chemin: empreinte}` d'un projet après avoir demandé à `collab` d'écrire ses documents ; les blobs sont adressés par SHA-256 et jamais supprimés. `writeFiles` et `deleteNode` modifient l'arborescence dans une transaction, et la passerelle de documents fait appliquer par `collab` le nouveau contenu des fichiers texte ouverts. Une file BullMQ `maintenance` exécute déjà une tâche périodique.

## Choix structurants

### Instantanés

- Table `snapshots` : projet, date, nature (`auto`, `compile`, `named`, `restore`, `git`), étiquette facultative, auteurs, manifeste, dossiers, empreinte du manifeste. Un instantané n'est créé que si l'empreinte diffère du précédent ; une version nommée est créée même sans changement (elle nomme l'état courant).
- Auteurs : chaque modification enregistre son auteur dans `project_activity` (projet, utilisateur, date). `collab` le fait à l'écriture d'un document, à partir des connexions qui l'ont modifié ; l'API le fait pour les opérations sur l'arborescence et les push Git. L'instantané prend les auteurs enregistrés depuis le précédent et vide la liste.
- Cadence : une tâche de maintenance, chaque minute, crée un instantané pour tout projet ayant de l'activité en attente et dont le dernier instantané a plus de 5 minutes ; une compilation réussie en crée un si l'état a changé. Un verrou Valkey par projet évite deux instantanés simultanés.
- Rétention (tâche quotidienne) : tout pendant 30 jours, puis le dernier de chaque heure jusqu'à 90 jours, puis le dernier de chaque jour ; les versions nommées sont gardées. Les blobs ne sont jamais supprimés à ce jalon (pas de ramasse-miettes), ce qui garantit qu'une version listée reste restaurable.

### Différences et restauration

- L'historique se consulte dans un panneau « Historique » de la page du projet : liste chronologique (date, auteurs, nature, étiquette), puis comparaison de deux versions, ou d'une version avec l'état actuel : fichiers ajoutés, supprimés, modifiés ; un clic affiche la différence ligne à ligne. Le calcul ligne à ligne se fait dans le navigateur avec `diff` (jsdiff, BSD-3-Clause, environ 10 kB gzip).
- Restaurer un fichier ou tout le projet : l'API prend d'abord un instantané de l'état courant, applique l'état choisi comme une transaction (fichiers texte remplacés par `collab`, donc visibles en direct ; binaires, créations et suppressions dans l'arborescence), puis prend un instantané de nature `restore`. Rien n'est effacé de l'historique.
- Une fonction unique `applyManifest(projectId, cible, origine)` sert à la restauration et au push Git.
- Versions nommées : bouton « Nommer cette version » et renommage ; téléchargement de toute version en zip.

### Pont Git

- Jetons personnels (`personal_access_tokens`) : nom, empreinte, quatre derniers caractères, expiration facultative, dernier usage, révocation. Gérés dans une page « Mon compte » ; le jeton n'est affiché qu'à sa création. Ils ne servent qu'à Git à ce jalon.
- `https://<hôte>/git/<projectId>` est servi par l'API, qui lance `git http-backend` (CGI) avec un environnement réduit. Caddy y transmet `/git/*`. Authentification HTTP Basic : nom d'utilisateur libre, mot de passe = jeton. Lecture pour tout membre, écriture pour éditeur et propriétaire. Échecs d'authentification limités en débit.
- Un dépôt nu par projet dans un volume `git-data`, créé à la première demande, branche `main`. À chaque annonce de références (`info/refs`), si l'état du projet diffère du dernier commit servi, l'API crée un commit à partir de `materializeProject` (plomberie Git : `hash-object`, `mktree`, `commit-tree`), auteurs de la période en co-auteurs.
- Push : `receive.denyNonFastForwards`, refus des suppressions de branche et des autres références que `main`. Un crochet `pre-receive` (script Node livré avec l'API) appelle une route interne de l'API, protégée par un secret propre au processus, qui : vérifie que l'ancien commit est le dernier servi et que le projet n'a pas changé depuis (sinon « tirez d'abord ») ; lit l'arbre poussé (`ls-tree -r`, `cat-file`) ; refuse liens symboliques, sous-modules, chemins hors projet ou invalides et fichiers trop gros ; applique l'arbre par `applyManifest` avec l'origine `git:<userId>`, puis prend un instantané de nature `git`. Un refus fait échouer le push avec le message.
- Taille d'un push plafonnée (100 Mio par défaut, `GIT_MAX_PUSH_BYTES`) au niveau de la requête HTTP et par `receive.maxInputSize`.

## Modèle de données

- `snapshots`, `project_activity`, `personal_access_tokens`, `git_repositories` (projet, dernier commit servi, empreinte du manifeste servi).
- Migration Drizzle versionnée.

## API

- `GET /api/projects/:id/history` (paginée), `POST /api/projects/:id/history` (version nommée de l'état courant), `PATCH .../history/:snapshotId` (étiquette).
- `GET .../history/:snapshotId/files` (manifeste), `GET .../history/:snapshotId/content?path=` (contenu d'un fichier d'une version), `GET .../history/compare?from=&to=` (`to` absent : état actuel), `GET .../history/:snapshotId/archive` (zip).
- `POST .../history/:snapshotId/restore` avec `{ path? }` (éditeur ou propriétaire).
- `GET|POST /api/tokens`, `DELETE /api/tokens/:id`.
- `/git/:projectId/info/refs`, `/git/:projectId/git-upload-pack`, `/git/:projectId/git-receive-pack`.

## Points tranchés

- P1. Pont Git dans l'API (SPEC §5) plutôt qu'un service séparé : l'API détient déjà accès, arborescence et blobs.
- P2. Le dépôt nu est un cache : il peut être reconstruit depuis les instantanés et l'état courant ; la sauvegarde (J10) l'inclut tout de même pour garder les identifiants de commit des clones existants.
- P3. Un push qui touche un projet modifié depuis le dernier fetch est refusé en entier (« tirez d'abord »), sans fusion côté serveur : Git fait la fusion chez l'utilisateur, avec ses outils.
- P4. Pas de synchronisation avec GitHub ou GitLab (P2 de §3.5) : J11.
- P5. Jetons limités à Git ; l'API REST reste accessible par session uniquement.

## Risques

- R1. `git http-backend` absent ou différent d'une image à l'autre : version de `git` figée dans l'image de l'API et testée en CI.
- R2. Push volumineux : plafonné en octets reçus et en taille par fichier ; un push refusé ne laisse aucun objet référencé.
- R3. Restauration pendant que d'autres éditent : la restauration remplace le texte en direct chez tous, comme un push ; c'est voulu et l'état précédent reste dans l'historique.
- R4. Volume de stockage des instantanés : seuls les fichiers modifiés produisent de nouveaux blobs.

## Bilan (2026-10-27)

### Ce qui fonctionne

- A1 : un projet est cloné avec un jeton créé sur la page « Mon compte », modifié localement et poussé ; l'éditeur ouvert affiche la ligne poussée sans rechargement (e2e). Les tests d'intégration de l'API couvrent clone, push avec ajout, modification et suppression de fichiers, conservation des dossiers vides et instantané `git` avec son auteur.
- A2 : une ligne tapée dans l'éditeur arrive par `git pull` (e2e, et intégration par l'API).
- A3 : une version nommée, puis modifiée, est restaurée depuis la fenêtre « Historique » ; l'éditeur revient au texte de la version, et la liste garde la version nommée, l'état remplacé et la restauration (e2e). Restauration d'un seul fichier et du projet entier couvertes en intégration.
- Push en retard refusé (le projet a changé depuis le dernier `git pull`), puis accepté après une fusion locale. Refusés aussi : autre branche que `main`, lien symbolique, push d'un lecteur, push au-delà de la limite de taille, jeton révoqué, personne non membre (intégration et e2e).
- Instantanés automatiques avec auteurs (activité enregistrée par `collab` et l'API), rien de nouveau quand l'état n'a pas changé, rétention par heure puis par jour avec versions nommées conservées, comparaison, contenu d'une version, archive zip, droits par rôle (intégration).

### Écarts au plan

- `git http-backend` n'est pas utilisé : il est dans le paquet `git-daemon` d'Alpine. L'API lance `upload-pack` et `receive-pack` en mode `--stateless-rpc`, ce que fait `http-backend` lui-même ; seul `git` est installé (`docs/decisions.md`).
- Le secret du crochet `pre-receive` est propre à chaque push et non au processus : il identifie aussi le projet et l'utilisateur, que le crochet n'a donc pas à annoncer.
- Les dossiers vides, que Git ne représente pas, sont conservés par un push ; un dossier vidé par le push disparaît.
- Variable `GIT_MAX_PUSH_MB` (en Mio) au lieu de `GIT_MAX_PUSH_BYTES`, comme les autres limites de l'instance ; `GIT_DATA_DIR` pour le dossier des dépôts.
- `applyManifest` s'appelle `applyState` (manifeste et dossiers). L'origine `git:<userId>` n'est pas stockée à part : l'instantané `git` porte l'auteur du push.
- Le verrou Valkey des instantanés est devenu un utilitaire commun (`apps/api/src/locks.ts`), utilisé aussi par le pont Git.

### Reste à faire, dette technique

- La construction de l'image de l'API télécharge `git` depuis les dépôts Alpine ; dans l'environnement de développement de ce jalon, ces dépôts étaient bloqués et l'image locale a été construite avec le `git` de l'image `alpine/git` (même version d'Alpine). La CI construit l'image normale.
- Les commits sont créés à la lecture ; un projet très gros (milliers de fichiers modifiés) allonge le premier `git clone` du temps de hacher les blobs. Les identifiants sont ensuite réutilisés.
- La sauvegarde du volume `git-data` est à intégrer au J10 ; un dépôt perdu est reconstruit depuis le projet, avec un nouvel historique Git (les clones existants devront être refaits).
- Synchronisation avec GitHub ou GitLab : J11.
